# Changelog

## 1.8.3

### The admin experience

- **A top-level menu with a page per section.** SendBeam lived at Settings → SendBeam behind seven tabs that appeared nowhere in the admin menu: to reach the pop-up settings you had to know the plugin was under Settings and then know the tab existed. Sixteen of the eighteen established plugins this was measured against take a top-level menu with their own icon; the one that does not compensates with a full-screen activation wizard, and this plugin had neither. There is now `add_menu_page()` at position 58.9 with the three-square mark as a base64 SVG, eight submenu items (Overview, Forms, Pop-ups, Audience, Site email, E-commerce, Settings, Help) and one router behind all of them. `options-general.php?page=sendbeam` and each of its tabs 301 to the page that replaced it, carrying any notice the old URL held, so every bookmark and every link in an old support reply still lands somewhere useful. The Plugins-screen "Settings" link points at the Settings page rather than at a dashboard.
- **A first run.** Activation sets a 30-second transient and the next admin page load goes once to `sendbeam-setup`: connect, verify your sending domain, switch on site email, place a form. It is guarded three ways — never during a bulk activation, never on a site that already has a key, and `apply_filters( 'sendbeam_setup_wizard', true )` switches it off for a host or an agency that sets these up itself. It renders inside `.wrap` with the admin menu and admin bar left alone, because a wizard that hides the way out is a wizard people close the tab on; **Skip this step** is on every step and **Go back to the Dashboard** is under all of them, and where somebody got to is kept in user meta so leaving and coming back resumes rather than restarts. Each step is the panel the matching settings screen already uses, so there is still one Connect button and one records table in this plugin.
- **`WP_List_Table` for the three lists.** Forms, the audience lists and the email log were hand-rolled `<table class="sb-table">`: no search, no pagination, no bulk actions, no empty state, and — the part that mattered — none of core's column collapsing, which is why Forms and Site email were the two screens that scrolled sideways at 393px. All three are subclasses now with a primary column, a per-page Screen Option and an empty state that says what to do next; the log gains a bulk delete. The two read-only lists return an empty `get_bulk_actions()`, which is core's own way of saying a list has none rather than offering a dropdown with nothing in it. There is no Resend row action on the log because the log keeps what a message was sent *to* and *about*, never its body — a Resend that could only send a different email is worse than no button.
- **The sending domain, in MailPoet's shape.** A "why" sentence, numbered steps, `<table class="widefat striped">` of Type / Host / Value with read-only fields that copy when clicked, a tick or "not found yet" per record, "DNS changes can take up to 24 hours", and three aggregate states instead of two: verified, pending (some records live, with a count) and not found. Pending and not-found looked identical before, and only one of them has work left in it.
- **The test email is an email.** It was two sentences of plain text. It is now a 600px table-based HTML message with a plain-text alternative, no images and no upsell, carrying the From name and address actually used, the sending domain and whether it is verified, the workspace, the plugin version and the time in the site's own timezone, then what happens now and one link to the email log.
- **Its result appears in the page, in WP Mail SMTP's shape**, replacing the form rather than becoming a notice: a success card with **Send another**, or a failure card with what went wrong, what it means, what to do — each mapped from the status code rather than dumping the API's own words — and a collapsible **Details for support** block holding the WordPress, PHP and plugin versions, where this site's key is kept (never the key), the domain state, the HTTP status and the raw error. It is captured at the moment the send fails and parked in a transient keyed to that administrator, because a raw error and a version list do not belong in an address bar, a server log or somebody's browser history.
- **Three Site Health tests and a debug section.** `sendbeam-key` (works / rejected / unreachable / limited), `sendbeam-domain` (verified?) and `sendbeam-mail`, which reports **critical** when site email is switched on behind an unverified domain — a site quietly sending its password resets from a domain no mailbox provider can check is worse off than one not using the feature. All three are `direct` tests reading the same minute-old cache the Overview reads, because a Site Health page that makes three HTTP requests is a Site Health page that times out. `debug_information` gains a SendBeam section, and the Help page prints the same values as one block with **Copy for support**.
- **Every message the plugin prints is an admin notice now.** Each screen used to echo its own `<p class="sb-msg">` somewhere in the middle of its own markup, so the answer to "did that save?" appeared in a different place on every screen and in the plugin's styling rather than WordPress's. They go through `wp_admin_notice()` (with a fallback, because that arrived in 6.4 and this plugin supports 6.1), in core's classes, dismissible, and only on SendBeam's own screens. The one exception is the setup notice, which is on the Dashboard and nowhere else, opens the wizard, and goes for good when it is dismissed or the site is set up.
- **A Help page** replaces the Docs tab: documentation links, system status with **Copy for support**, who to ask (hello@sendbeam.io, the WordPress.org forum, GitHub issues), the shortcodes and the permissions table.
- **The design system loses four foreign signals and keeps the rest.** Labels were 10px uppercase mono with 0.1em tracking — nothing else in the eighteen-plugin study styled anything that way. They are sentence case at 13px now, and mono is kept for the things people copy: values, code and figures. Primary buttons use `var(--wp-admin-theme-color)` with white text rather than black, so a site running Midnight or Ocean gets a button that belongs to it; secondary is an ink outline and danger a vermilion outline, because a filled red button beside a filled blue one is a coin toss at a glance. Fields are label-above and 40px with the focus ring in the same theme colour, every on/off setting is a switch, `.sendbeam-app` has the same margin on both sides, and core's `button-primary` appears nowhere in the plugin's own markup — only inside a core notice, where a brand-styled button is the thing that looks pasted in.
- **Every remaining `.sb-table` sits in the `.sb-scroll` wrapper the plugin already owned**, and that wrapper gained `contain: inline-size`, without which a table wider than the screen scrolls inside its box *and* widens the page anyway in a mobile browser — which is the exact failure the class exists to prevent.

- **"SendBeam's shared address" was being said about the customer's own domain.** The shared-host test was "anywhere under the app's domain", so any site whose sending domain is a subdomain of `sendbeam.io` — every site on the staging host, and any customer using one — was told its own verified domain was SendBeam's shared address. `shared` now means an exact match on `post.<app host>` or `mail.<app host>`, the two hosts the platform actually sends shared mail from. Nothing else under that domain is shared, and a domain that is the site's own verified sending domain never reaches the test at all, because that is settled first and settled for good, whatever it happens to be a subdomain of.
- **The test email carried the same contradiction, and the owner read it on a phone.** "From address ws-…@post.sendbeam.io" sat two rows above "Sending domain wp-test.sendbeam.io — verified", under a headline saying the site could send email through SendBeam. Every row of it is now derived from `sendbeam_effective_sender()`: the headline qualifies itself (`… from yourdomain.com` / `… (from the shared address for now)`), the From row says what kind of address it is, a new **Signed by** row names the domain that actually authenticated the message so a reader can compare the two at a glance, and the sending-domain row distinguishes "verified and in use" from "verified, but not in use yet" and "not verified yet". Where something is left to do, a **Next step** block sits above "What happens now" with the button that does it — press Send from your domain, or add the DNS records. The in-page result mirrors it: a successful send from the shared address is a success card plus an amber note, which is how WP Mail SMTP words the same case.
- **The test email now declares its colour scheme.** Apple Mail inverts a message that says nothing about dark mode, which turned the ink band into paper and every address in the table into a blue auto-detected link. `color-scheme` and `supported-color-schemes` are declared, every cell states its own `bgcolor` and colour, and `a[x-apple-data-detectors]` is put back to the table's own styling. Below 480px the label sits above its value rather than taking a quarter of a 380px screen and wrapping a URL mid-word.
- The three workspace figures stay in a row of three on a phone — stacked, three single digits took half the card — and only break below 340px. The recent-email rows swap the site's date format for a short one (or the time, for today), the address truncates with an ellipsis, and the result stays whole and right-aligned instead of wrapping onto a line of its own.
- **The DNS records are readable on a phone.** Four columns in 393px left the host and the value about ninety pixels each — "resend._dc" — on the one screen whose entire job is reading them accurately. Below 782px each record becomes a block: type and verdict on one line, then host, then value, each full width and free to wrap, in a textarea rather than an input because an input cannot wrap at any width. On desktop the value column takes the space Type and Found do not need, and the field's height comes from its line box rather than being pinned — a pinned height on a 12px mono field was clipping its own descenders, so the underscore in `resend._domainkey` simply vanished.
- **One connected card, however the key arrived.** A site with a pasted key was shown "Connected" in the header band and **Connect this site** in the card underneath — the plugin arguing with itself about its own state, which is what the owner saw on the phone. There is one card now: what it is connected to, a muted line saying how ("via Connect" / "using an API key"), and the one thing a connected card is for. **Reconnect** joins **Disconnect** only where there is a connection to re-make; a pasted key has none. No primary button, and no sales sentence — replacing a key is a settings job and lives under Settings.
- **The upgrade to Connect is offered where a pasted key actually falls short**, and nowhere else: the sending-domain step when `domain_state` is `no_site` or `no_permission`, worded "Switch to one-click Connect" rather than "Reconnect with more permissions", which is not what a pasted key would be doing. It carries to the site-email step queued behind it, because the way out is the same link and offering it only on the step somebody is not standing on is one hop too many.
- **Disconnecting a pasted key no longer revokes it.** `POST /connect/disconnect` revokes the calling key, and a key somebody pasted was minted for whatever they minted it for — very possibly another site. It is forgotten here, left alone there, and the confirmation and the notice both say which of the two happened.
- **"No idea" is no longer said as "no".** A pasted key records no permissions, so `sendbeam_connect_granted()` answered false for all of them and the site-email step announced that the key "was not given permission to send your site's email" — a claim about somebody's key that this site has no way of making. `sendbeam_connect_permissions_known()` tells the three cases apart: the step stops claiming, the one-click **Switch on** is offered rather than hidden, and SendBeam decides on the first message.
- **Run the setup guide again**, on the Help page. Every plugin in the field study that has a wizard keeps one reachable. It resets where this person got to and touches nothing else — `sendbeam_setup_done` is the site's answer to "has anybody set this up?", and re-reading the guide is not un-setting-up a site.
- **The Overview could tell a site owner two true things that added up to a lie.** The sending-domain step said "harbourlane.co.uk is verified. Email from this site will be sent from your own domain" while the From address in the site's own settings was still `ws-…@post.sendbeam.io` — SendBeam's shared address. Both sentences were right. Together they were wrong, and nothing on the screen distinguished them. `sendbeam_effective_sender()` is now the single answer to "what does this site send as?", classifying the address as `own_domain`, `shared`, `other` or `none` — derived from the app host rather than a hardcoded list, so a self-hosted SendBeam classifies its own shared addresses correctly. Step 2 says only that the domain is verified. Step 4 says what is really happening, is amber rather than ticked when the site is sending as SendBeam from a verified domain or from a domain nothing has verified, and carries a one-press **Send from yourdomain.com**. The connection line names the kind of address, not just the address.
- Enabling site email once the domain verifies now puts the From address on that domain — the workspace sender when it is already there, `hello@<domain>` when it is not — rather than filling in the shared address blind. A shared address Connect itself wrote earlier is corrected when the domain lands; an address the owner typed is never touched.

- **The email log is a table, not twenty rows in an option.** `sendbeam_mail_log` held the last twenty attempts in wp_options: a reasonable shape for "did my test send work?" and a useless one for a real site, where a shop doing thirty order emails an hour lost the morning by lunchtime, the list table could page through at most one screen, and every write rewrote and re-autoloaded the whole array. `{$wpdb->prefix}sendbeam_mail_log` now takes one row per message, created by dbDelta on activation and behind a `sendbeam_db_version` check on `admin_init` — because a plugin updated by uploading a zip over the top fires no activation hook, and a site whose table was never made would just fail quietly on every send. Per-site on multisite, since the prefix is.
- The screen it feeds grew up with it: search across the address, the subject and the reason a message failed; All / Sent / Server mailer / Failed views with a count on each, and a view nothing landed in is not a link to an empty screen; sortable by date and by result; a per-page Screen Option; bulk delete. A **Sent by** column names the plugin that asked for the message, worked out from the backtrace because `wp_mail()` carries no caller — read once per send, for one column, never for a decision.
- **Retention is the site owner's choice**: 7, 30 (the default) or 90 days, or for ever, pruned by a daily `sendbeam_mail_log_prune` event that activation schedules and deactivation clears. On top of it a hard cap of 20,000 rows, oldest first, whatever the setting says — "for ever" is a promise about time, not about disk space, on hosting that is very often not the owner's.
- **Clear the log** is a button on the Site email screen behind its own closed confirmation, and deliberately **not** a bulk action: "Delete" and "Delete all" one mis-click apart in the same dropdown is how somebody loses the log they came to read.
- Existing entries migrate on the first page load after updating, newest first with their original timestamps — a log claiming every message arrived at the moment of the upgrade is worse than no log. The option is deleted as part of the move, so a second run finds nothing and cannot duplicate anything. Uninstall drops the table and the version option.
- Bodies are never stored, in any column. A log exists to answer "did it go, and if not why"; keeping the contents of every password reset a site has ever sent is a liability nobody asked for.
- **The Pop-ups screen was the one place that looked like a different product.** Each rule was a `<fieldset class="sb-rule">` on the paper grey with a black `<legend>` tag, while every other screen in the plugin is white cards with ink rules. A rule is now that same card: a header carrying "Pop-up 1", the Active switch and Remove, and a body of label-above fields. Numbered because the order is the rule — the first pop-up that matches a page is the one that opens — and the cards renumber themselves after an add or a remove, so the numbers cannot start lying. Eyebrow and Button label were half a line out from each other, because the grid bottom-aligned fields while one of them carried helper text; they are a two-column row with helper text under each and the grid aligns labels at the top. Every field name and value is unchanged, so what saves is exactly what saved before.
- **Something red flashed under Disconnect on every refresh.** The confirmation shipped open in the markup so a browser with no JavaScript could still submit it, and was hidden by script on load — so it drew, then vanished, on every single render of the Overview. It is a native `<details>` now: the summary is the Disconnect button, the box it opens holds the confirmation and the form, it is shut until somebody presses it, and pressing it again is the way out. No script touches it, and it works with JavaScript off. Note that Chrome exposes a `<summary>` as a disclosure rather than as a button — more accurate, since it carries its own expanded state, but a change from the `<button>` it was.
- The same fault, smaller, on the Site email screen: the From name, From address and fallback rows were drawn and then hidden on load whenever site email was off. They arrive hidden from the server now, and the switch only takes over when somebody actually moves it.

- **Disconnect did not disconnect.** `register_setting()` hangs the form's sanitiser on `sanitize_option_sendbeam_settings`, so **every** `update_option( 'sendbeam_settings', … )` runs the rules written for a posted form — including the writes the plugin makes on its own behalf. Disconnect wrote an empty API key, the rule "a blank key field keeps the saved key" put the old one straight back, and the site stayed connected. The owner pressed the button twice.
- The same trap had two quieter faces. A posted form names its tab, so only that tab's keys are touched; a programmatic array names none, so every key counted as posted — which meant the rule that releases `mail_enabled`, `mail_from_name` and `mail_from_email` from `sendbeam_connect_filled` fired on **every** programmatic write, undoing what Connect had just recorded, and `mail_enabled` was re-derived from "is the box in the array" on writes that simply did not mention it.
- Programmatic paths now go through `sendbeam_write_settings()`, which stores the array as-is — it is already what the plugin means — and still does the one piece of housekeeping that applies, forgetting what was cached under a key that changed. All four writers (Disconnect, the Connect exchange, the site-email switch-on and the workspace-move release) use it, and a test asserts that they are still the only four. `sendbeam_settings` is the only registered option, so it is the only place this could happen.
- The test stubs ran no sanitiser on `update_option()`, which is why this passed every test while failing on a real site. They now run whatever `register_setting()` registered, exactly as WordPress does; fixtures seed values directly instead.

### Bugs a live install found

- The list-table classes extended `WP_List_Table` at plugin-load time. Core does not load that class until wp-admin is well underway, so Forms, Audience and Site email were fatal errors on a real site while the smoke tests passed — the stubs define the class before the plugin loads. They are required when a screen asks for them. The tests gained the assertion that would have caught it, and a second one asserting that every hook this plugin registers names a function that exists.
- The wizard was registered with an empty parent, which routes correctly and then leaves `get_admin_page_title()` with nothing to find: WordPress hands a null to `strip_tags()`, which is a deprecation notice on PHP 8 and a browser tab reading "— WordPress". Its parent is `options.php`, which is in no menu.
- The Connect consent checkboxes rendered ticked and looked empty. Core fills the box with the admin theme colour and draws a white tick on it; forcing the background white left a white tick on white.

### What a QA sweep found

- **Pressing Save on one card of the Forms screen emptied the other.** Forms is one tab with two cards and two Save buttons, and the sanitiser grouped its fields by tab: whichever card you did not press arrived missing from `$_POST` and was written as empty. Saving Appearance cleared `contact_form`, `[sendbeam_contact]` renders nothing without it, and a published contact page went to an empty box for every visitor with "Settings saved." on screen and nothing in the log. Field groups are per form now, not per tab.

- **Site email could be switched on with no key, and three screens then disagreed about what was happening.** Disconnecting leaves the switch on, which is right — reconnecting should not make the owner hunt for it again — and with no key nothing goes near SendBeam: every message leaves by the server's own mailer exactly as before. The screens said otherwise. The test email told the owner to tick a box that was already ticked and never mentioned a key; Site Health raised a **critical** alarm about email being sent from an unverified domain, about email that was not being sent. There is one helper answering why site email is not running — the switch, or the key — the ticked box says which where it is ticked, the test email names the key, and Site Health reports a recommendation to connect the site instead of a red flag about a thing that is not happening.

- **The test email described the message the site asked for, not the one that arrived.** SendBeam does not refuse a message whose From sits on an unverified domain — it accepts it and substitutes the workspace's own sender. So a test email arrived from `ws-…@mail.sendbeam.io`, signed `d=mail.sendbeam.io`, carrying a card that said "From address: hello@wp-test.sendbeam.io", "Signed by: wp-test.sendbeam.io" and "SendBeam refuses messages from it". Three claims, all contradicted by the headers of the message printing them. `sendbeam_effective_sender()` now works out the address that actually goes out, the domain that actually signs it and whether those differ from what was asked for; the From row names the substitution, **Signed by** is the real signer, and the next step says SendBeam sent it under its own address rather than that it refused to.

- **"SendBeam could not be reached", straight after SendBeam answered.** `domain_state: unavailable` wears two opposite meanings — the plugin's, "the request failed", and SendBeam's, "I could not set that domain up, and here is why". Only the first was in the sentence, so a site that had just connected successfully was told SendBeam was unreachable while its cached status held `ok: true` and "That domain is already registered" in two places. The step prints the reason SendBeam gave when the answer came from SendBeam, and keeps the unreachable wording for the case it was written for.

- **The setup guide ticked steps nobody had done.** The rail ticked every step whose number was below the current one, and **Skip this step** is on every step — so opening step 3 on a site with no API key showed "✓ Connect · ✓ Sending domain" above a body reading "This step needs a connected site. Go back to step 1", while the Overview's own checklist said neither was done. The rail reads the same answer the checklist does.

- **"A SendBeam pop-up is live on the site" with every rule switched off.** The checklist asked whether any pop-up rule had ever been saved. A rule that is unticked, or has no form chosen, puts nothing on the site — the front end serves no loader at all — so the step ticked itself on evidence the visitor could not see. There is one helper for "could this actually show somebody a pop-up", and the checklist uses it.

- **`[sendbeam_contact]` takes an `id` now**, because the Forms screen offered a Copy button on every contact row and told the owner to "place it by shortcode". There was one shortcode for all of them and it always rendered the default, so copying the one beside "Wholesale enquiry" put the Contact-us form on the page. Every row names its own form; a bare `[sendbeam_contact]` still renders the default, so nothing already on a page changes.

- **"Connected by: A pasted key" on a site with no key.** The Help page's system status — the block a site owner pastes into a support request, so the first thing support reads — answered a two-way ternary about how the key arrived without a third case for there being no key, directly under "API key: Not set". The sending-domain state was blank on the same block. Both say what is true now, and no field in that block is ever empty.
- **Forms and Audience blamed the permissions of a key that did not exist.** Both screens branch on a `null` that means either "the key was refused" or "there is no key", and read only the first: a disconnected site was told "Your forms cannot be read with the current key. Give it the Forms (read) permission in SendBeam", under a header band already saying "Not connected". They say the site is not connected, and where to connect it.

- **"Remove the saved key" on Settings → Advanced left a Connect-issued key live in the workspace, and said nothing.** The Overview's Disconnect revokes such a key at SendBeam and its confirmation says so; the Advanced tab's checkbox is a second, quieter door to the same place and it cleared the option and stopped. The owner who tidied up there was left holding a live key for a site that no longer exists as far as they are concerned. Both doors go through one function now, and the field says which of the two things removing this particular key will do — revoke it, or merely forget it — before it is removed.

- **Reconnecting destroyed the sending domain the site already had.** The consent page prefilled SEND FROM from `site_url` on every run, so pressing Reconnect for any other reason — more permissions, a changed workspace, a key rotation — re-set the sending domain to this site's own host and took the existing one out of the workspace, along with the DNS records the owner may have been half-way through entering. Nothing warned them; the records were simply gone and the hourly re-check unscheduled. A reconnect now passes the domain the site already has, read from the status body, so the consent page offers it back. The one link whose purpose is choosing a different one — "Sending from the wrong domain?" — deliberately passes nothing, and neither does a first connect.

- **The longest DNS host was cut off inside the field you are told to click.** The wrapping rule lived only inside the ≤782px media query, so the phone case that had been complained about was fixed and the desktop one was not: at 1280px the Host column is about 282px and `resend._domainkey.mail.<domain>` does not fit in it. Click-to-copy still copied the whole value, but somebody comparing what they pasted into their registrar against what is on screen could not see the end of it. The field wraps at every width now, and keeps `overflow: auto` so a browser with no JavaScript scrolls to the rest rather than hiding it.

- **Check now comes back to the screen it was pressed on.** The check is offered on the Overview and on Settings → Sending domain and always landed on the Overview, so somebody working through the DNS records was moved to a different screen to be told the result and had to navigate back to carry on.
- **The page about the sending domain said less than the checklist did.** Step 2 on the Overview carried the reason SendBeam gave; Settings → Sending domain dropped it, on the screen dedicated to the subject. There is one sentence for "this site has no sending domain" now, and where SendBeam's own note already says what to do, the plugin stops appending a second instruction naming a different SendBeam screen.

- **Every "you do not have permission" was served as HTTP 500.** `wp_die()` with no status argument defaults to a server error, so all sixteen of the plugin's admin-post actions answered an Editor's POST with a 500 — a correct refusal, logged everywhere as a fault in the plugin. They answer 403. (The nonce refusals were already right: `check_admin_referer()` sends 403 itself.)

- **The permissions list named this site's host, not the domain that was chosen.** The domain scope's label interpolates the host the consent page was asked about, which is right on a consent page and a description of the request rather than the outcome on a connected site: a site connected with SEND FROM set to `mail.harbourlane.co.uk` read "Set up this site's sending domain (harbourlane.co.uk)" ever after. The connected card names the domain the workspace actually has.

### Connect

- **Connect SendBeam.** Onboarding was four steps before the plugin did anything: make an account on sendbeam.io, verify a domain, create an API key with the right permissions, paste it back. Every one of those was somewhere to stop. The Overview tab's first step is now a button: tick what this site may do, create the account or sign in in a pop-up on sendbeam.io — with the site name and the administrator's email address already filled in — and the site is handed a key with exactly those permissions.
- The plugin is the client in that exchange and never trusts the browser with the key. The pop-up comes back with a single-use grant, not a key; the key is fetched server-to-server from this site's own PHP (`POST /api/v1/connect/exchange`); and `state` — minted here, kept in a transient belonging to one administrator, and deleted the moment it is read — is the CSRF token, because a nonce cannot survive a redirect from another origin.
- The key is written through the same `sendbeam_sanitize_settings()` path a pasted key goes through, so there is one set of validation rules rather than two. Pasting or removing a key by hand clears the Connect marker, and **Disconnect** is the existing "Remove the saved key" path — it forgets this site's copy, and says plainly that the key stays valid in SendBeam until revoked there.
- Pasting a key still works, moved into a quiet "I already have an API key" disclosure under the button.
- `uninstall.php` now sweeps `sendbeam_connect_*` transients for every administrator, not just the one doing the uninstalling.
- **The sending domain, in the plugin.** A fifth permission — "Set up this site's sending domain (yourdomain.com) in SendBeam", ticked by default — lets consent add this site's domain to the workspace. The Overview then shows its DNS records as a table with a Copy button on every value, a **Check now** button that asks SendBeam to look the DNS up again without leaving wp-admin, and a **Set up DNS automatically** button where the registrar supports one-click set-up. This was the gap: a site owner who has just connected needs the domain next, and had to go and find it on sendbeam.io.
- The set-up checklist is four steps, with the sending domain second. It used to say "optional" about the one thing every other step depends on, and step three now ticks off only when a block or shortcode is actually on the site rather than when a form has been chosen in the settings.
- Site email fills its From name and address from the workspace sender, but switches on **only** when the sending domain is verified — at consent time, from the **Check now** button, or from a one-click **Switch on**. A site whose password resets silently stop arriving is worse off than one that never turned the feature on. Turning site email off by hand cancels that held-back switch-on, so a later check never quietly undoes the decision.
- **Disconnect** is a visible button on the connected card, confirmed inline rather than with `window.confirm()`, and it revokes the key at SendBeam (`POST /api/v1/connect/disconnect`) before forgetting it here. The old path was a "Remove the saved key" checkbox that left a live key in the workspace and told you to go and revoke it yourself.
- Disconnect will not revoke a key defined as `SENDBEAM_API_KEY` in `wp-config.php`. That key beats the saved one everywhere, including in the revoke call, so pressing the button on such a site would have taken down a key Connect never issued and something else is probably using. The stored key is forgotten, nothing is revoked, and the screen says where the live one is.
- A blocked pop-up is no longer a dead end: the Connect form falls back to navigating the current tab, and the page it lands on offers **Back to the site** instead of trying to close a window nothing opened.
- The Overview screen itself is now covered by the smoke tests. No test could see a settings screen before, which is how a permission check or a form on the page layer could drift without anything noticing.
- **The sending host is the owner's to choose.** The consent page suggests this site's domain and takes another if you type one, and the plugin shows `domain.name` from the answer rather than deriving a host from `site_url`. A brand domain or a `mail.` subdomain was previously impossible from either end.
- **Every DNS record carries the check's verdict.** Two records right out of three looked exactly like none of them. Never-checked is kept apart from not-found, because telling somebody their DNS is wrong when nothing has looked at it is its own bug. Every record SendBeam asks for is a CNAME, so the table says nothing about priority — an always-empty Priority column is a box people go hunting for at their registrar.
- **A missing sending domain says which of four things happened.** `domain: null` meant the box was never ticked, the key predates domains being readable, the key has no site host, or the row was removed by hand, and step 2 answered "not set up" to all of them. The status now carries `domain_state` and a sentence, and every word step 2 says comes from the answer rather than from what the site remembers granting — which is what made a site with a pasted key announce a missing permission while printing that domain's records underneath.
- **Reconnecting no longer means disconnecting first.** A step whose sentence names a permission you did not give offers **Reconnect with more permissions**, which starts the ordinary Connect flow with every box preselected; the connected card carries a plain **Reconnect** asking for what the key already holds.
- **Disconnect puts back what Connect filled in, and only that.** The form it chose, the sender it worked out and the site email it switched on are recorded as they are filled, and released again the moment you save that tab by hand. A default form belonging to a workspace this site no longer has a key for makes every embed 404 without a word, which is what used to happen. The workspace keeps its list, form, domain and sender; the confirmation says so.
- **The DNS is checked again without anybody watching**, hourly for a day after connecting, completing the held-back switch-on when the domain verifies and stopping as soon as there is nothing left to find out. Records almost never spread while somebody is still in wp-admin. Deactivating the plugin clears the event — there was no deactivation hook at all before.
- **Automatic DNS comes back to WordPress.** The one-click link carries this site's Overview as its return address; the page it lands on says whether the registrar added the records, spends exactly one check, and takes the flag off the address bar so a refresh does not check again.
- **"Put a form on the site" looks where forms actually are**: every public post type, block templates and template parts, block widgets, the text widgets a sidebar really holds, and the layouts page builders keep in post meta — plus the form's own hosted URL alongside the block and the shortcodes. The step says where it found one, and "I've placed it elsewhere" ticks it on your word, with a way back.
- **The Overview never waits ten seconds for a panel.** Screen renders ask with a four-second timeout and fall back to the last answer they had, marked as old; the answer is kept for half a day rather than the minute it is trusted for.
- **One cached status per key, hashed.** Two administrators signed in to different workspaces shared a single transient, so for up to a minute each was shown the other's sending domain and told to put its records into their own DNS. The key is hashed because a transient name ends up in the options table, in backups and in logs.
- **A key pinned in `wp-config.php` is no longer offered a Connect button.** It beats anything stored in the database, so connecting minted a real key, saved it and never used it. The panel and the connected card say where the live key is and how to change it.
- "Last checked" is rendered with the site's own date and time formats and timezone instead of the API's ISO string.
- A key pinned in `wp-config.php` now hides the paste field as well as the button: a key saved in the database would lose to the constant on every request, so offering somewhere to put one was offering to create a problem.
- Reconnecting into a different workspace forgets the cached status of the old one before it asks about the new one. It was possible to spend a minute looking at the previous workspace's sending domain and be told to put its records into your DNS.
- The way out of a missing permission is offered on the step somebody is standing on, not only on the step it is queued behind. Site email waiting on a domain that is waiting on a box nobody ticked was one hop too many.
- The sending-domain step says how to change the domain as well as how to finish it. That is precisely when somebody notices they have set up the wrong one, and the point at which every other sentence on the step has stopped talking to them.
- "I've placed it elsewhere" is offered whenever the workspace has a form at all, rather than only when a default has been chosen. A form named in its own shortcode is still a form on the site, and those sites had an untickable step and no way to say so.
- Coming back from a registrar says the check has run, in the past tense, because by the time anybody reads it the step underneath is already showing what it found. "Checking now…" promised a page that was about to change and then never changed.
- The first step's link points at the Connect button rather than at the paste field underneath it.

## 1.8.0

- **E-commerce events (WooCommerce).** A new tab feeds SendBeam's three native e-commerce automation triggers: Order placed (from WooCommerce's own order-processed hook — reliable, and keeps a running `lifetime_value` total on the contact), Product viewed (only for a known contact: logged in, or an email already given this visit — never anonymous tracking) and Cart abandoned. Each is its own switch, off by default.
- **Cart abandoned is a real, working best-effort heuristic**, built on wp-cron the same way `includes/bridges.php` already queues form-plugin subscriptions: adding to cart timestamps the shopper's session, a one-off cron event checks after a configurable window (default 60 minutes) whether an order followed, and fires once if not — and only for a cart where an email became known at some point. WooCommerce has no native "abandoned cart" event, which is why dedicated cart-recovery plugins exist as a category; this is documented plainly as a heuristic, not a guarantee, on the settings screen and in the README.
- Deliberately a new function for Order placed rather than a change to the existing checkout opt-in hook in `includes/sync.php` — one is a marketing-consent tick box, the other a store event that needs no consent, and tangling them would make both harder to reason about.
- `uninstall.php` removes the new options, un-schedules the new cron hooks, and sweeps the per-session cart-tracking transients.
